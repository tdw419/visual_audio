The core constraint to design around: GPUs win through **SIMT lockstep** — many threads executing the *same* instruction at the *same* time, with divergent branches serialized (predicated execution costs you the full cost of every path taken across the warp). A single RISC-V core interpreting arbitrary branch-heavy kernel code is the worst-case input for that model — there's no way to make *one* core emulator "GPU-fast" by tuning it; the shape of the problem has to change.

Three real directions, in order of how well they fit both "genuine speedup" and what this project is actually building toward:

**1. Many independent cores in parallel — throughput, not latency.** Run N guest cores simultaneously, one per GPU thread, instead of one core per dispatch. Individually each core is still slow (same ~1M instr/s), but aggregate throughput across thousands of lanes could genuinely exceed a CPU. This only works if you don't fight divergence: guests in the same warp need to be doing roughly the same *kind* of work at the same time, or you eat the serialization cost anyway. Practically this means: many copies of the *same* small program (not one big diverse kernel) — which happens to match this project's actual product shape (pixel-encoded programs, PXC1/VAC1) far better than "boot one Linux kernel."

**2. ### 1. What's already parallel in Linux, and what that parallelism actually is

Linux scales to hundreds of cores, but by **partitioning and localizing state**, not by eliminating serialization — it pushes serialization down to fine grain rather than removing it:

- **Per-CPU data** (percpu variables, per-CPU run queues): avoids cross-core contention by giving each core its own copy. This is spatial partitioning across O(10²) independent execution contexts, not O(10³–10⁵) SIMT lanes running the same instruction stream.
- **RCU**: lets readers proceed lock-free by never mutating in place — writers create a new version and defer reclamation until all pre-existing readers finish. This eliminates reader-side serialization specifically; writers still serialize among themselves. It's a trick for a specific access pattern (read-mostly, rare-write), not a general parallelism strategy.
- **io_uring**: asynchronous completion queues avoid blocking syscall-per-op overhead, but the underlying work (an actual read, an actual write) still executes serially somewhere — io_uring parallelizes *submission*, not the operation itself.
- **Lock-free structures**: reduce contention cost, don't eliminate the underlying coordination requirement.

The scaling story is real but it's coarse-grained (tens to low-hundreds of independent-ish execution contexts, each still fundamentally sequential internally), achieved by minimizing *cross-core* coordination — categorically different from SIMT's model of thousands of lanes executing in lockstep on the *same* instruction stream. Linux's SMP scaling is evidence kernels can avoid needless serialization, not evidence they can become embarrassingly parallel.

### 2. What's fundamentally serialized, and why it resists this shape specifically

- **Context switching**: this is definitionally about time-multiplexing one physical core across multiple logical threads. - **Interrupt handling**: inherently per-CPU and inherently sequential in the sense that a core can only be in one context (interrupted or not) at a time. Not a shared-state serialization problem, a physical-model problem.

fn mem_read(addr: u32, width: u32, is_signed: bool) -> u32 {
    let raw = mem_read_u32(addr);
    let byte_offset = (addr & 3u) * 8u;
    
    switch (width) {
        case 1u: { // Byte
            let byte_val = (raw >> byte_offset) & 0xFFu;

                return byte_val | 0xFFFFFF00u;
            }
            return byte_val;

            if (is_signed && (half_val & 0x8000u) != 0u) {
                return half_val | 0xFFFF0000u;
            }
            return half_val;
        }
        default: { // Word
            return raw;
        }
    }

### Atomic Memory & Sub-Word Refactoring Plan

Because multiple GPU threads access the shared `ram` buffer simultaneously, all memory mutations must use WebGPU atomic primitives to prevent data races and torn reads/writes.

#### 1. 32-Bit Atomic Operations (RV32A / Standard Stores)

* **Direct Mapping:** 32-bit operations map directly to native WGSL atomics:
* `atomicStore(&ram[idx], val)`
* `atomicLoad(&ram[idx])`
* `atomicAdd(&ram[idx], val)`
* `atomicExchange(&ram[idx], val)`
* `atomicAnd(&ram[idx], val)` / `atomicOr(&ram[idx], val)` / `atomicXor(&ram[idx], val)`
* `atomicMin(&ram[idx], val)` / `atomicMax(&ram[idx], val)`



#### 2. Sub-Word Atomic Stores (Byte / Halfword via CAS Loop)

Non-atomic read-modify-write causes silent data corruption when two harts write adjacent bytes in the same 32-bit word. Sub-word writes must use a Compare-And-Swap (`atomicCompareExchangeWeak`) loop:

```wgsl
fn atomic_store_subword(byte_addr: u32, value: u32, width: u32) {
    let word_idx = byte_addr >> 2u;
    let shift = (byte_addr & 3u) * 8u;
    let mask = select(0xFFFFu, 0xFFu, width == 1u) << shift;
    let prepared_val = (value << shift) & mask;

    var old_val = atomicLoad(&ram[word_idx]);
    loop {
        let new_val = (old_val & ~mask) | prepared_val;
        let cas_res = atomicCompareExchangeWeak(&ram[word_idx], old_val, new_val);
        if (cas_res.exchanged) {
            break;
        }
        old_val = cas_res.old_value;
    }
}

```

#### 3. Emulating RV64 64-Bit Atomics (`AMO*.D`)

WebGPU storage buffers do not provide native 64-bit atomics. RV64 atomics (`AMOADD.D`, `AMOSWAP.D`, `LD.D`/`SD.D`) must be synchronized across adjacent 32-bit word pairs:

* **Split CAS Strategy:** Execute a spin-lock CAS loop on the low word (`word_idx`) to claim ownership, perform the high-word mutation (`word_idx + 1`), and release the lock via atomic exchange on the low word.
* **Lock-Free Fast Path:** For read-only aligned 64-bit access, verify generation counters or split high/low load stability checks.

#### 4. Load-Reserved / Store-Conditional (`LR.W` / `SC.W`)

* **Tracking State:** Each hart tracks its active reservation in `lr_reservation_addr` and `lr_reservation_valid`.
* **Execution:**
* `LR.W`: Load the address, store `byte_addr` into `harts[hart_id].lr_reservation_addr`, and set `valid = 1u`.
* `SC.W`: Check if the reservation is still valid. If valid, attempt `atomicCompareExchangeWeak` at `target_addr`. If the CAS succeeds, clear the reservation, write `0` (success) to `rd`. If the CAS fails, write `1` (failure) to `rd`.
