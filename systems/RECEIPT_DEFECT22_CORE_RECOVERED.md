## 3. Recovering the core (the format cost two wrong attempts)

`CoreDump: base64` is the **last** field of an apport report, and its payload is **not one base64 stream**:
apport writes it as a sequence of *independently* encoded chunks, one per line, each prefixed by a single
space, wrapping a gzip stream. Measured failure modes of the cheap approaches:

1. joining the (space-prefixed) lines and decoding once → gzip dies with
   `Error -3 while decompressing data: invalid code lengths set` (each chunk's padding lands mid-stream);
2. filtering "base64-looking" lines and decoding → `EOFError: Compressed file ended before the
   end-of-stream marker was reached` (the leading–space continuation rule is the field boundary).

What works (committed as `tools/apport_core_unpack.py`): decode **per line**, then concatenate the *bytes*,
then inflate:

```
core: …pytest___init__.py.1000.crash -> /tmp/pytest_v2.core (1193254912 B on disk, 1193254912 B inflated)
```

1,193,254,912 B ELF core, ~4 s, re-runnable at any time from the preserved report.

**Established:**

1. The fatal signal is a **genuine** SIGSEGV, not a timeout or an abort: the log says
   `Fatal Python error: Segmentation fault` (faulthandler's real-fault wording), and the core's top frames
   are faulthandler **re-raising** (`pthread_kill(sig=11)`) after its dump — the standard
   dump-then-`raise(signum)` path.
2. The interrupted context (#5 → #6) places the faulting PC at **`0x5e3259` inside `/usr/bin/python3.12`**:
   `nm -D` brackets it as *after* `_PyEval_EvalFrameDefault` (`0x5d6630`) and *before* `PyEval_GetGlobals`
   (`0x5e38e0`), i.e. inside the interpreter binary's own code, **not inside a C extension**. The ticket's
   earlier wording ("a C-level call under `step`", read as an extension fault) is sharper than the evidence;
   the `_check_alignment` frame the first reading blamed is absent from the dump for the same reason.
3. Process shape at death: **32 threads** — 1 crashing + 31 parked in `__futex_abstimed_wait_common64`
   (idle pools), consistent with 35 resident native extensions (torch/numpy/PIL) loaded but not running.

**Not established (no claim made):**

- the **exact faulting instruction/address**. The kernel's original `siginfo`/`ucontext` was consumed by
  faulthandler's handler before the re-raise: `$_siginfo` in the core is the *second* signal's
  (`si_addr = 0x3e8002ff471`, meaningless for `raise()`), and per-frame register reconstruction through the
  signal frame without `python3.12-dbg` is unreliable (`frame 5` shows `rdi=0xba6748`, `rip=0x5e3259`, but
  that is unwinding through a debug-less signal frame, so it is not offered as the fault).
- heap corruption vs stack overrun vs wild pointer — **no mechanism claimed**; #5's neighbourhood is inside
  CPython's dispatch code and that is the whole of it.
- whether the 05:32:44 `/usr/bin/python3.12` report is the same class: apport's own log attributes it to the
  SUITE-ISO-1 harness's *deliberate* synthetic crash (`script: …/pytest/__init__.py … test_crash.py`), and
  its embedded core is truncated (16 KB report, process already gone) — unusable.

## 5. Capture path: corrected, and one silent blocker removed

Measured from `/var/log/apport.log` (not reasoned):

- apport writes **two different things**: a report + embedded gzip core in `/var/crash/` for *packaged*
  executables (this is how the pytest crash was kept), and a **raw core** in `/var/lib/apport/coredump/`
  for *unpackaged* ones — both of my probes landed there as raw cores
  (`core._usr_bin_python3_12.1000.…3377603…` 7,008,256 B; `core._tmp_d22cap_crashprobe.1000.…3379919…`
  319,488 B).
- **A non-zero `RLIMIT_CORE` is required**, and it is environmental, not guaranteed: the log carries
  `core limit 0` for the 05:33 / 05:53 / 07:44 crashes and
  `core limit 18446744073709551615 … treating as unlimited` for the two probes run with `ulimit -c unlimited`.
  A crash under `core limit 0` leaves nothing.
- **The silent blocker:** while a report for an executable sits in `/var/crash` *unseen*, apport refuses the
  next one — `report … already exists and unseen, skipping to avoid disk usage DoS`
  (`/usr/lib/python3/dist-packages/apport/fileutils.py:719`). That line fired **four times** in one day
  (05:33:04, 05:33:52, 05:53:03, 07:44:14). So DEFECT-22's own report was *disabling* all future core
  capture for the arc's executable.

**Actions taken (both reversible, evidence preserved):**

1. `tools/arc_lega.sh` now raises the limit explicitly (`ulimit -c unlimited 2>/dev/null || true`, with the
   rationale in a comment) so a crash in an arc run always has a core to recover.
2. The two reports were **moved** (not deleted) out of `/var/crash` to
   `~/glyph_evidence/crashes/` (`DEFECT22_20260913_051810_arcLegA_pytest.crash`,
   `synthetic_20260913_053244_isoHarness_python312.crash`, plus a README naming the original apport keys).
   `/var/crash` is now empty, so the next crash of either executable is captured again.
