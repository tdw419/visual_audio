BM802 FAULT-SENSITIVITY MAP -- one medium byte XOR'd: how far does the boot get?

Fixture (rung8/bm802_fixture.py) re-bakes the loader's EXPECTED_CRC to the CRC the
corrupted payload actually computes, so the guest gate stays a REAL check and what
is measured here is kernel tolerance, not gate function (BM903 L6 measured that).
Primitive: one byte XOR 0xA5 (three bits); a one-bit leg is reported separately.
RECOVERED is absent by construction -- nothing on this medium can repair a fault
until Rung 6 is funded and built.

Control: 3/3 boots reached stage 5 (median 11.0s); fault legs ran on a 38s budget derived as 3x that median, so the ceiling is measured, not chosen.

stage  meaning                                verdict
  5    boot scripts finished                      INERT (the fault did not matter)
  4    reached "Loading extensions"               SENSITIVE unless it timed out
  0-3  refused / silent / never reached init      SENSITIVE
  6    + serial prompt                          bonus only (BM903 measured the autologin race)

Weighted by region size: 5.82 MB of the 13.64 MB medium (42.6%) sits on a byte where a single-byte fault stops the boot. That assumes each region is uniform between its samples -- the map is a SHAPE, not a census: 303 of 13,640,192 medium bytes were perturbed.

METHOD CHECK on setup-header -- reported apart and NOT counted in the
weighting above, because it re-covers the same 119 bytes.
Stride 4 B sampled 30 bytes and read 10% fatal; the
census booted the other 89. The whole window is 15/119
= 13% fatal, and the stride saw 3 of those
15: a fixed stride aliases one byte per field, so a field can be
fatal in bytes the stride never touched.
  The stride MISSED 12 fatal byte(s): 0x202, 0x203, 0x204, 0x23c, 0x23e, 0x23f, 0x250, 0x254, 0x256, 0x257, 0x262, 0x263.
  => A stride can hide fatal bytes, so every fatal% in the table above is a
     SAMPLE, not a rate -- and for the question Rung 6 asks ("how much of the
     medium must stay readable?") they are to be read as a FLOOR.

Read this against the Rung 6 case: a large SENSITIVE area is the argument FOR
paying +75% medium capacity for Hamming(7,4), because decay then equals a box that
will not boot; a large INERT area is the argument that some of the medium can be
left unprotected -- and it is also the warning, because an INERT byte is a fault
the CRC gate happily signs off on. Silence is not the same as correctness.
