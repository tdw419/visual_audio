# `reproduce_prereqs.sh` in a pristine checkout — and BM653's pair over the tree it made

Made 2026-09-20. The claim this file exists to support is narrow and worth
stating exactly: a closed row can be brought up from **the commit**, given one
vendor blob, with no working files hand-carried from the lane that built it.

The commands, in this order, in a scratch tree that held nothing but committed
source:

    T=/tmp/bm000_cold
    git -C <repo> archive HEAD tools/bare_metal_poc | tar -x -C $T
    mkdir -p $T/tools/bare_metal_poc/rung7           # rung7/ is untracked: absent
    cp rung7/core.gz $T/tools/bare_metal_poc/rung7/  # the one input not in git
    cd $T/tools/bare_metal_poc && bash reproduce_prereqs.sh   # log 1
    cd rung6_5 && bash run_bm653_e2e.sh                        # log 2

Two facts about the tree this was run in, both true of the commit it describes
and recorded here rather than hidden: `rung7/` has no tracked files, so a clean
checkout has no `rung7/` **directory** until it is made and fed — and
`reproduce_prereqs.sh` itself was untracked when this ran, so it was copied in
by hand. Committing it is what removes the second one. Disk: 91 % full, 3.3 GB
free, so both scratch trees were deleted after these captures.

## The refusals bite — four ways to break the input, each checked

A gate that only ever prints OK is the defect this whole pass exists to remove,
so each refusal leg was exercised rather than read. All four ran in the scratch
tree above against a copy of the script; each exits 1, and the real script and
input were restored afterwards.

1. **`core.gz` replaced** (9,260,807 B of `/dev/urandom`, same size, so only the
   content differs) — `rung7/core.gz sha256 35e6528194f1344b... != the pinned
   7f1e370dd4e489fd...` then `REFUSE: the payload is derived from this file; a
   different initrd is a different ancestor`, rc=1, before any step runs.
2. **`core.gz` absent** — `REFUSE: no initrd, nothing can be built`, rc=1.
3. **One landmark pin moved** (bit 0 of `bm903_stage1.bin`'s expected sha
   flipped in the script) — `[RED ] rung9/bm903_stage1.bin sha256
   f0e7d7e1c6ab4536... != the landed aaaaaaaa... -- rung9 bm903_mkimg.py did not
   reproduce it. Stop: a row gate run on top of this would be measuring a
   different ancestor.` then `PREREQ_STATUS=RED (1)`, rc=1. The message names
   the step that owns the file, which is the `STEP_OF` table's whole job.
4. **A generated-but-tracked file hand-edited** (one line appended to
   `rung9/bm903_px_layout.inc`, the case BM602's receipt warns about — editing
   a `.inc` the asm includes) — three REDs and `PREREQ_STATUS=RED (3)`, rc=1:
   the loader step fails to assemble, its product therefore goes missing from
   the landmark table, and the TRACKED leg reports the edit itself
   (`moved under the regeneration: 4185c0a2c1cfbddb... -> c252f2dc7df65635...`).
   The regeneration rewrites the file back to the committed bytes, so the tree
   is healed by the next run — but not silently: the RED says so first.

Test 3 is the closest analogue to what BM802's `bm802_pin_bitest.py` does for
its own stage1 pin: a deliberately wrong expected value, and the check has to
say so.
