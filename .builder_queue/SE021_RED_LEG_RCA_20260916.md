## Root cause: data-over-code aliasing through the GH-8b FS window

1. `build_exec_shell` places the exec branch's `FILE_READ` dest (`xread_addr`)
   at **word 1090**, inside the GH-8b FS pixel window `[1024,1280)`
   (`tools/glyph_isa_v2.py:668`). `SYSCALL 0x04` writes the child's output
   bytes there via `_fs_pix_write` → **image pixels**, at scanline
   `word*2 → row 68, cols 4..19` (32 px/row at W=8; measured: 1090*2=2180,
   2180//32=68).
2. The shell's per-turn Region-B stamp prologue (ST-stamping
   runner/child/out path constants, ~3 bytes/branch-path + nulls) is
   **length-proportional to those paths**. With pytest's ~70-char tmp paths
   (`/tmp/pytest-of-jericho/pytest-N/<test>/glyph_child_runner.py`) the
   prologue occupies pixel rows ~18..**68** — i.e. the program itself
   extends into the FS window's pixel rows (window = rows 64..80).
3. Turn 1 (`x`): exec succeeds, `FILE_READ` writes 8 bytes to word 1090 →
   **overwrites its own instruction pixels at row 68** with `CHILD_OK`.
4. Turn 2 (`e hello`): prologue re-runs from (0,0), executes 399 clean
   LDI/ST steps, reaches `(4, 68)` — now RGB (0,72,67) (`0x4843` = "CH") —
   `rgb_to_opcode → None` → `step()` sets `running=False` **silently**
   (`tools/glyph_isa_v2.py:763-765`). No fault word, no output, empty echo.
   Gate asserts `'' == ' hello'` → RED.

## Why it looked n=1-flaky but isn't

Short external repro paths (e.g. `/tmp/se021_trace2_xxx/...`, ~50 chars)
keep the prologue above row 66 → no overlap → the same two-turn sequence
passes. Gate is **deterministically red under pytest path lengths**, green
under short-path repros. Ten consecutive pytest runs: 1F/3P every time
(2026-09-16 01:0x). The :158 failure is one mechanism, not noise.

## Evidence chain (all measured this tick, /tmp only)

- Mirror of the leg run from /tmp under pytest: reproduces
  `['CHILD_OK', '']` (runner path len 77).
- Per-opcode trace of turn 2: 399 steps LDI/ST (rows 18..67), terminal
  `(4, 68, None)`; registers r0..r12 zeroed except stamp constants.
- Ring state at end of turn 2: `len=7 cursor=0` — the input ring was seeded
  but never read (CPU never reached the first `SYSCALL 0x02` of the turn).
- Pixel decode of the freshly built image: row 68 pre-run decodes as valid
  instructions (`LDI/ST...`); the corruption only exists after turn 1's
  `FILE_READ`, matching `[SYSCALL] FILE_READ: 8 bytes ... to addr 1090`.

## Fix options (sibling lane's design call — cheapest first)

(a) **Move FILE_READ dests out of the window** — plain RAM below word 1024
    (read buffers are transient data, not persisted files). Caveat: the
    assembler's image-space-write tracker keys FILE_READ's dest off a known
    register constant; a RAM dest interacts with the RAM-vs-pixel LD check
    (the reason the current code LDI'd r8 directly — see the comment block
    above `:exec_branch`).
(b) **Assert the layout invariant in `build_exec_shell`**: no program
    instruction row may fall in [window_lo_row, window_hi_row] = [64, 80]
    given the actual baked path lengths. Turns silent self-corruption into a
    loud build error, but does NOT by itself make the leg pass.
(c) **Relocate the program region below the window** (pad/offset so code
    starts under row 80) — larger layout change, touches every build path.

## What this PASS would not prove

If (a) or (c) lands and the gate goes green: it proves the two-turn
control-returns leg at pytest path lengths; it does not prove WGSL parity of
the exec path, nor freedom from aliasing at other path lengths unless the
(b)-style invariant is also enforced.
